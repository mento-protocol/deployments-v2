## TL;DR

We propose zeroing the Broker's orphaned trading-limit configurations for Mento v2 exchange pools that have been deprecated and destroyed.

---

## Overview

As part of the migration from Mento v2 virtual pools (BiPoolManager) to Mento v3 (Router/FPMM), deprecated v2 pools are removed in three steps:

1. The pool's VirtualPool adapter is deprecated on the `VirtualPoolFactory`, removing it from Router routing (Mento Labs Safe transaction).
2. The exchange is destroyed on the `BiPoolManager` via `destroyExchange` (Mento Labs Safe transaction).
3. **This proposal**: the Broker's trading-limit configurations for the destroyed exchange are zeroed via `configureTradingLimit(exchangeId, token, config)` with all limits and flags set to zero.

Step 3 requires governance because the Broker is owned by the Mento Governance Timelock.

### Why zero the trading limits?

`BiPoolManager.destroyExchange` does not clean up the Broker's trading-limit config and state, which are keyed by `exchangeId ^ token`. Leaving them in place is harmless while the exchange does not exist, but the stale configuration would silently resurrect if an exchange with the same id (same token symbols and pricing module) were ever recreated. Zeroing them keeps the Broker's state consistent with the set of live exchanges.

### Security Considerations

- The transactions only touch trading-limit configuration for exchange ids that no longer exist on the BiPoolManager.
- No ownership changes, no implementation upgrades, and no funds are involved.

### Transaction Details

The exact list of `configureTradingLimit` calls is generated by `script/actions/DeprecateExchangePools.s.sol` from the exchanges flagged `deprecated` in the network configuration, and can be independently verified by re-running the script in dry-run mode against the current config.
