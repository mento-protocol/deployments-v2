## TL;DR

We propose lowering the trading limits on the exchanges that remain in Mento v2, replacing the current time-windowed limits (L0/L1) and global limit (LG) with a single global limit per asset equal to the stable's current total supply (and its USD equivalent on the USDm side). This allows the existing supply to fully contract back into collateral while preventing any meaningful supply growth.

---

## Overview

As part of the migration from Mento v2 to Mento v3, most stable assets are being migrated to the v3 CDP model. The FX stables covered by this proposal (AUDm, CADm, ZARm, COPm, BRLm, PHPm, GHSm, NGNm, KESm, XOFm) will instead remain on the v2 model: their exchanges on the BiPoolManager stay live and swaps continue to be routed through the Broker.

Since these stables are not being migrated, we want to constrain how much their supply can grow while they remain on v2 — without ever trapping existing holders. This proposal replaces each remaining exchange's trading-limit configuration on the Broker — currently a combination of a 5-minute limit (L0), a 1-day limit (L1), and a lifetime global limit (LG) — with a global-only limit (LG) for both assets of each exchange:

- **FX asset**: the FX token's current total supply (rounded up to whole tokens).
- **USDm**: the USD equivalent of that supply at the current oracle rate.

For each asset, the limit is first **reset** (configured with no flags, which clears the accumulated global netflow) and then set to the new global-only value, so the new limits apply from a clean slate rather than on top of historical netflow.

### Why supply-sized global-only limits?

- Setting the limit below the current supply would prevent the supply from fully contracting if holders wanted to exit the stable back into reserve collateral. Sizing the limit at exactly the outstanding supply (1x) guarantees the exit path while capping growth at effectively zero net new supply.
- The time-windowed limits (L0/L1) exist to smooth flow on actively growing pairs; for pairs intentionally kept static, a single lifetime cap is simpler and stricter.
- Trading limits are denominated in whole tokens (the Broker scales amounts by the token's decimals before applying them).

### Security Considerations

- The transactions only touch trading-limit configuration on the Broker for existing, live exchanges.
- No ownership changes, no implementation upgrades, and no funds are involved.

### Verification

The proposal script (`script/migration/MGP18.sol`) enforces state checks around the limit changes:

- **Before**: every affected pair has a live exchange on the BiPoolManager and a trading limit configured on both assets.
- **After**:
  - Both assets of every affected pair have a global-only limit — L0 and L1 fully cleared, LG flag set, and the global limit equal to the FX supply / its USD-equivalent respectively.
  - **Full-exit simulation**: for each pair, the FX token's entire current supply is swapped back to USDm through the Broker (in a snapshotted simulation), proving the new limits do not block the supply from fully contracting into collateral.

### Transaction Details

The exact list of `configureTradingLimit(exchangeId, token, config)` calls (a reset followed by the new global-only config per asset) is generated by the script from on-chain state — token total supplies and oracle rates at proposal creation time — and can be independently verified by re-running the script in dry-run mode.
